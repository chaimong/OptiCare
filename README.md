# ดูดีการแว่น — ระบบบริหารจัดการร้านแว่นตา (OptiCare Pro)

เว็บแอปพลิเคชันแบบ Single-Page Application สำหรับร้านแว่นตา ครอบคลุมแดชบอร์ด ฐานข้อมูลลูกค้าและค่าสายตา
คลังสินค้า การเปิดบิลและติดตามงานแล็บ พร้อมผู้ช่วยแนะนำเลนส์ที่ประมวลผลในเบราว์เซอร์แบบออฟไลน์

## 2. การเปิดใช้งาน

### วิธีที่ 1 — ดับเบิลคลิก `index.html`
ใช้งานได้ทุกฟีเจอร์ **ยกเว้น** การซิงค์ Google Sheets เพราะเบราว์เซอร์มองไฟล์ `file://` เป็น origin `null`
ซึ่ง Google ปฏิเสธด้วยนโยบาย CORS

> ทดสอบยืนยันแล้ว: จาก origin `null` เบราว์เซอร์รายงาน *“No 'Access-Control-Allow-Origin' header is present”*
> แต่จาก origin `https://` ปกติ ได้ `status 200` และ `response.type === "cors"` — ปัญหาอยู่ที่วิธีเปิดไฟล์
> ไม่ใช่การตั้งค่าแชร์ของชีต

### วิธีที่ 2 — เปิดผ่านเว็บเซิร์ฟเวอร์ (แนะนำ)
จำเป็นถ้าต้องการซิงค์ข้อมูลจาก Google Sheets

```bash
npx serve .
```

หรือ

```bash
python -m http.server 8000
```

แล้วเปิด `http://localhost:8000`

### การเข้าสู่ระบบ

เข้าสู่ระบบด้วย **ชื่อผู้ใช้และรหัสผ่าน** ที่ผู้ดูแลสร้างให้ ไม่มีรหัสผ่านฝังอยู่ในโค้ดหน้าเว็บ
และเซิร์ฟเวอร์ตรวจสิทธิ์จากตาราง `Users` ทุกคำขอ
รายละเอียดการตั้งค่าอยู่ในหัวข้อ **ระบบยืนยันตัวตนและสิทธิ์** ด้านล่าง

## 3. ระบบยืนยันตัวตนและสิทธิ์

ระบบใช้ **บัญชีผู้ใช้ + รหัสผ่าน** ที่ผู้ดูแลสร้างให้ ไม่พึ่งบริการล็อกอินภายนอกใด ๆ
ไม่ต้องตั้งค่า OAuth ไม่ต้องมีบัญชี Google และเปิดหน้าเว็บผ่าน http ธรรมดาก็ทำงานได้

### ลำดับการทำงาน

1. ผู้ดูแลสร้างบัญชีจากเมนูในสเปรดชีต — ระบบ**สุ่มรหัสผ่านชั่วคราว**มาให้แล้วแสดงครั้งเดียว
2. หน้าเว็บส่ง `{ username, password }` ไปที่ `action=login` ผ่าน **POST เท่านั้น**
   (บังคับ POST เพื่อไม่ให้รหัสผ่านติดไปกับ URL แล้วไปโผล่ใน log ของเซิร์ฟเวอร์)
3. เซิร์ฟเวอร์แฮชรหัสผ่านด้วย **salt ประจำบัญชี + pepper ลับ** แล้วเทียบกับค่าในตาราง `Users`
4. ถ้าผ่าน ออก **session token** อายุ 8 ชั่วโมง เซ็นด้วย HMAC-SHA256
5. ทุกคำขอถัดไปต้องแนบ session token และผ่าน `authorize_()` ตรวจบทบาทกับ `ACTION_PERMISSIONS`

### การเก็บรหัสผ่าน

| เก็บที่ไหน | อะไร |
| --- | --- |
| ชีต `Users` | `passwordSalt` (สุ่มต่างกันทุกบัญชี) และ `passwordHash` |
| Script Properties | `PASSWORD_PEPPER` กุญแจลับที่ใช้แฮช — **ไม่ได้อยู่ในชีต** |
| ไม่เก็บที่ไหนเลย | รหัสผ่านจริง |

`passwordHash = base64( HMAC-SHA256( salt + ":" + รหัสผ่าน , pepper ) )`

salt ที่ต่างกันทำให้พนักงานสองคนที่ตั้งรหัสผ่านเหมือนกันได้ค่าแฮชคนละค่า
ส่วน pepper อยู่นอกชีต คนที่ถูกแชร์ไฟล์ Google Sheets ให้ดู **จึงเดารหัสผ่านย้อนกลับไม่ได้**
แม้จะเห็นค่าแฮชทั้งคอลัมน์ก็ตาม

> **ข้อจำกัดที่ควรรู้:** Apps Script รันช้าและไม่มี PBKDF2/bcrypt ในตัว ระบบจึงใช้ HMAC รอบเดียว
> ไม่ได้วนซ้ำหมื่นรอบแบบมาตรฐานเว็บขนาดใหญ่ ความปลอดภัยหลักมาจาก pepper ที่อยู่คนละที่กับชีต
> ถ้าใครได้ทั้ง Script Properties และชีตไปพร้อมกัน เท่ากับได้สิทธิ์เต็มอยู่แล้วโดยไม่ต้องถอดรหัสผ่าน

### มาตรการอื่นที่ใส่ไว้

| เรื่อง | สิ่งที่ทำ |
| --- | --- |
| เดารหัสผ่าน | กรอกผิดติดกัน 8 ครั้ง ล็อกบัญชีนั้น 15 นาที (ปลดได้จากเมนู) |
| เดาว่ามีบัญชีนี้ไหม | รหัสผิดกับไม่มีบัญชี ตอบข้อความ**เดียวกัน**เสมอ |
| รหัสชั่วคราวค้างในระบบ | บัญชีที่ผู้ดูแลตั้งรหัสให้ ถูกบังคับเปลี่ยนรหัสเองก่อนใช้งาน |
| รหัสผ่านอ่อน | ต้องยาว ≥ 8 ตัว และมีทั้งตัวอักษร (ไทยหรืออังกฤษ) กับตัวเลข |
| ข้อมูลรั่วผ่าน API | `listUsers` / `me` ไม่เคยส่ง `passwordHash` หรือ `passwordSalt` ออกไป |
| แอบใส่แฮชเอง | `saveUser` ตัดค่า `passwordHash` / `passwordSalt` ที่ส่งมาทิ้งทุกครั้ง |
| token ถูกขโมย | เมนู **ยกเลิกทุกเซสชัน** เปลี่ยนกุญแจ ทุก token ตายทันที (รหัสผ่านไม่กระทบ) |

### บทบาทและสิทธิ์

| บทบาท | ดูข้อมูล | เปิดบิล | บันทึกผลตรวจ | จัดการสต็อก | จัดการผู้ใช้ | โครงสร้างฐานข้อมูล |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| `owner` | ✅ | ✅ | ✅ | ✅ | ✅ ทุกบัญชี | ✅ |
| `admin` | ✅ | ✅ | ✅ | ✅ | ✅ ยกเว้นบัญชี owner | ตรวจได้ ซ่อมไม่ได้ |
| `optometrist` | ✅ | ✅ | ✅ | ❌ | ❌ | ❌ |
| `staff` | ✅ | ✅ | ❌ | ✅ | ❌ | ❌ |
| `viewer` | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |

`admin` แต่งตั้งใครเป็น `owner` ไม่ได้ และแก้ไข/ปิดบัญชี `owner` ไม่ได้ — กันการยกระดับสิทธิ์ตัวเอง
ระบบยังบังคับให้เหลือ `owner` ที่เปิดใช้งานอยู่อย่างน้อยหนึ่งคนเสมอ และปิดบัญชีตัวเองไม่ได้

แก้สิทธิ์ได้ที่ `ACTION_PERMISSIONS` ใน `Code.gs` จุดเดียว

### ขั้นตอนติดตั้ง

1. เปิดไฟล์ Google Sheets ของร้าน → เมนู **OptiCare › ติดตั้งฐานข้อมูลครั้งแรก**
2. เมนู **OptiCare › 👤 สร้างบัญชีผู้ดูแลคนแรก** → ตั้งชื่อผู้ใช้ (เช่น `admin`)
   ระบบสุ่มรหัสผ่านชั่วคราวมาให้ — **จดไว้ทันที เปิดดูย้อนหลังไม่ได้**
3. เปิดหน้าเว็บ → เข้าสู่ระบบด้วยชื่อผู้ใช้และรหัสชั่วคราวนั้น
4. ระบบบังคับให้ตั้งรหัสผ่านใหม่ทันที
5. เพิ่มพนักงานได้ 2 ทาง
   * หน้าเว็บ → ปุ่ม **ผู้ใช้ระบบ** บนแถบหัว (มีปุ่มสุ่มรหัสผ่านให้)
   * สเปรดชีต → เมนู **OptiCare › 👤 เพิ่มบัญชีผู้ใช้**

### เมนูจัดการบัญชีในสเปรดชีต

| เมนู | ใช้เมื่อ |
| --- | --- |
| 👤 สร้างบัญชีผู้ดูแลคนแรก | ติดตั้งครั้งแรก (ใช้ได้เฉพาะตอนยังไม่มี owner) |
| 👤 เพิ่มบัญชีผู้ใช้ | เพิ่มพนักงานใหม่ |
| 🔑 ตั้งรหัสผ่านใหม่ให้ผู้ใช้ | พนักงานลืมรหัสผ่าน |
| ปลดล็อกบัญชีที่กรอกรหัสผิดหลายครั้ง | พนักงานถูกล็อก 15 นาที แต่ต้องใช้งานเดี๋ยวนี้ |
| ดูรายชื่อผู้ใช้ | ดูว่าใครยังไม่ได้ตั้งรหัส ใครถูกล็อก ใครเข้าล่าสุดเมื่อไร |
| ยกเลิกทุกเซสชัน | สงสัยว่า token รั่ว |

### การจัดการความปลอดภัยระหว่างใช้งาน

| ต้องการ | ทำอย่างไร | ผลที่เกิด |
| --- | --- | --- |
| พนักงานลืมรหัสผ่าน | เมนู **ตั้งรหัสผ่านใหม่ให้ผู้ใช้** | ได้รหัสชั่วคราว และถูกบังคับเปลี่ยนเองตอนเข้าครั้งแรก |
| ตัดสิทธิ์พนักงานที่ลาออก | ปุ่มปิดใช้งานในหน้าผู้ใช้ระบบ | เข้าไม่ได้ทันที แม้ session ยังไม่หมดอายุ |

## 4. โหมดการเชื่อมต่อฐานข้อมูล

กดไอคอนเฟืองบนการ์ด **“การเชื่อมต่อฐานข้อมูล”** ที่แผงควบคุมเพื่อเลือกโหมด

| โหมด | อ่าน | เขียน | ต้องตั้งค่าอะไร |
| --- | --- | --- | --- |
| **ข้อมูลในเครื่อง (Local)** — ค่าเริ่มต้น | localStorage | localStorage | ไม่ต้อง |
| **Google Sheets โดยตรง** | gviz (อ่านอย่างเดียว) | ❌ เขียนกลับไม่ได้ | แชร์ชีตแบบ “ผู้ที่มีลิงก์ดูได้” + เปิดหน้าเว็บผ่าน http/https |
| **Apps Script API** — แนะนำ | ✅ | ✅ เขียนขึ้น Google Sheets | Web App URL จาก `Code.gs` |

### การล็อกหน้าจอในโหมดออฟไลน์

โหมดออฟไลน์และโหมดอ่านอย่างเดียวไม่มีบัญชีผู้ใช้ ปุ่ม **ออกจากระบบ** จึงทำหน้าที่เป็น **ล็อกหน้าจอ**
บังข้อมูลลูกค้าไว้เมื่อต้องลุกจากเคาน์เตอร์ และ**จำสถานะไว้ข้ามการรีโหลดหน้า**
(เก็บใน `localStorage` คีย์ `opticare:locked:v1` — กดปุ่ม “กลับเข้าใช้งาน” เพื่อปลดล็อก)

> ⚠️ การล็อกนี้ไม่มีรหัสผ่าน จึงกันได้แค่สายตาคนที่เดินผ่าน **ไม่ได้ป้องกันผู้ที่เข้าถึงเครื่องได้จริง**
> หน้าจอล็อกเขียนข้อความนี้ไว้ตรง ๆ เพื่อไม่ให้เข้าใจผิดว่าปลอดภัยแล้ว
> ถ้าต้องการความปลอดภัยจริงต้องใช้โหมด Apps Script API ที่มีบัญชีผู้ใช้และรหัสผ่าน

ปุ่ม **เชื่อมต่อเซิร์ฟเวอร์เพื่อใช้บัญชีผู้ใช้จริง** บนหน้าจอล็อกเปิดหน้าต่างตั้งค่าได้ทันที
(หน้าต่างนี้ตั้ง `z-index` ไว้สูงกว่าหน้าจอล็อก จึงเปิดทับได้ ขณะที่ `#app-shell` ยังคง `inert`
ข้อมูลลูกค้าที่อยู่ข้างหลังจึงยังเข้าถึงไม่ได้) เมื่อบันทึกแล้วระบบจะพาไปหน้าเข้าสู่ระบบให้เอง

### ตั้งค่าโหมด Apps Script API

1. ติดตั้ง `Code.gs` ตามหัวข้อ 10 แล้ว **Deploy › New deployment › Web app** — คัดลอก URL ที่ลงท้ายด้วย `/exec`
2. เมนู **OptiCare › สร้าง API Token** ในสเปรดชีต — คัดลอก token
3. ในเว็บแอป กดเฟือง → เลือก **Apps Script API** → วาง URL และ token → **ทดสอบการเชื่อมต่อ** → **บันทึก**

เมื่อเชื่อมต่อแล้ว ระบบจะ**เขียนขึ้น Google Sheets อัตโนมัติ**ทุกครั้งที่บันทึกลูกค้า ผลตรวจ สินค้า
เปิดบิล หรือเปลี่ยนสถานะงานแล็บ โดยยังบันทึกลงเครื่องไว้ด้วยเสมอ —
ถ้าเซิร์ฟเวอร์ไม่ตอบ ข้อมูลไม่หาย ส่งขึ้นใหม่ได้ด้วยปุ่ม **ส่งข้อมูลในเครื่องขึ้นเซิร์ฟเวอร์**

## 4. การเก็บข้อมูล

ข้อมูลลูกค้า สินค้า และออเดอร์ถูกบันทึกอัตโนมัติลง `localStorage` ของเบราว์เซอร์

## 5. โมดูลคำนวณทางทัศนมาตรศาสตร์

สูตรทั้งหมดอยู่ในหมวด `2b. CLINICAL CALCULATIONS` ของ `script.js` เป็น pure function
แยกจากการแสดงผลเพื่อให้ตรวจสอบและแก้ไขได้ง่าย

| ฟังก์ชัน | สูตร / เกณฑ์ | ใช้ที่ไหน |
| --- | --- | --- |
| `sphericalEquivalent(sph, cyl)` | SE = SPH + CYL/2 | แฟ้มลูกค้า, ผู้ช่วยแนะนำเลนส์, ใบสั่งงานแล็บ |
| `astigmatismType(axis, cyl)` | WTR แกน 0–30/150–180 · ATR แกน 60–120 · Oblique นอกช่วง (ระบบ Minus Cyl) | แฟ้มลูกค้า, ผู้ช่วยแนะนำเลนส์ |
| `transpose(sph, cyl, axis)` | SPH+CYL / −CYL / AXIS±90 | แสดงค่าในระบบ Plus Cylinder |
| `anisometropia(...)` | \|SE ขวา − SE ซ้าย\| | ธงเตือน, ผู้ช่วยแนะนำเลนส์ |
| `vertexCompensate(power, shiftMm)` | F′ = F / (1 − x·F) | ค่าสายตาสูง, เทียบกับคอนแทคเลนส์ |
| `estimateEdgeThickness(...)` | s = y²·\|F\| / 2000(n−1) + ความหนากลาง | ตารางเปรียบเทียบวัสดุ, ใบสั่งงานแล็บ |
| `decentration(A, DBL, monoPD)` | (A + DBL)/2 − Mono PD | ใบสั่งงานแล็บ |
| `minimumBlankSize(ED, dec)` | ED + 2·\|dec\| + 2 มม. | ใบสั่งงานแล็บ |
| `parseVA(va)` | รองรับ 6/6, 20/20, ทศนิยม → LogMAR = −log₁₀(decimal) | ธงเตือนการมองเห็นต่ำ |
| `progressionRate(history)` | ΔSE เฉลี่ยสองตา ÷ ระยะเวลา (ปี) | แฟ้มประวัติ, รายการเฝ้าระวัง |

### เกณฑ์เฝ้าระวังทางคลินิก (`CLINICAL_THRESHOLDS`)

| เกณฑ์ | ค่า | ความหมาย |
| --- | --- | --- |
| `highMyopia` | SE ≤ −6.00 D | สายตาสั้นระดับสูง — แนะนำตรวจจอประสาทตาประจำปี |
| `highHyperopia` | SE ≥ +4.00 D | ภาระการเพ่งสูง ควรตรวจ Binocular vision |
| `highAstigmatism` | \|CYL\| ≥ 2.00 D | ต้องระบุแกนแม่นยำ เตือนช่วงปรับตัว |
| `anisometropia` | ≥ 2.00 D | เสี่ยง Aniseikonia และ Prismatic imbalance |
| `rapidProgression` | ≥ 0.50 D/ปี | พิจารณาแนวทางชะลอสายตาสั้น |
| `reducedVaLogMAR` | > 0.30 | แก้ด้วยแว่นแล้วยังไม่ถึงเกณฑ์ ควรส่งต่อจักษุแพทย์ |
| `recallMonths` | 12 เดือน | ถึงกำหนดนัดตรวจซ้ำ |
| `vertexCriticalPower` | ≥ 4.00 D | ต้องบันทึกและชดเชยระยะ Vertex |

แก้ค่าเกณฑ์ได้ที่ออบเจกต์ `CLINICAL_THRESHOLDS` จุดเดียว ระบบจะอัปเดตทั้งธงเตือน
รายการเฝ้าระวัง และข้อความคำแนะนำให้สอดคล้องกันเอง

> ค่าที่คำนวณได้เป็นเครื่องมือช่วยตัดสินใจสำหรับผู้ประกอบวิชาชีพ ไม่ใช่การวินิจฉัยทางการแพทย์
> ความหนาขอบเลนส์เป็นค่าประมาณจากสูตร Sagitta ค่าจริงขึ้นกับผู้ผลิตและ Base curve ที่ใช้

## 6. แฟ้มประวัติการตรวจ (Longitudinal Record)

ลูกค้าหนึ่งรายเก็บผลตรวจได้หลายครั้ง (`customer.history` เรียงใหม่→เก่า) โดย `customer.refraction`
คือผลตรวจล่าสุดเสมอ

* เมื่อแก้ไขแฟ้มลูกค้า ระบบจะ **บันทึกเป็นการตรวจครั้งใหม่** เป็นค่าเริ่มต้น เก็บผลเดิมไว้ในแฟ้ม
* ยกเลิกตัวเลือกนั้นเฉพาะกรณีแก้ไขข้อผิดพลาดของผลตรวจล่าสุด (ระบบจะเตือนแบบ destructive)
* ผลตรวจวันเดียวกันจะถูกแทนที่ ไม่สร้างรายการซ้ำ
* ข้อมูลรูปแบบเดิมที่มี `refraction` ชุดเดียวจะถูกแปลงเป็นแฟ้มประวัติ 1 รายการอัตโนมัติ

### แก้ไข / ลบ รายการในแฟ้มประวัติ

ตารางแฟ้มประวัติมีคอลัมน์ **จัดการ** ให้แก้หรือลบผลตรวจ**ย้อนหลังรายรายการ** ไม่ใช่เฉพาะรายการล่าสุด

| ปุ่ม | ทำอะไร |
| --- | --- |
| ✏️ แก้ไข | โหลดค่าของผลตรวจรายการนั้นขึ้นฟอร์ม พร้อมแถบสีเหลืองบอกว่ากำลังแก้วันที่ไหน — กดบันทึกแล้ว**เขียนทับรายการนั้น** ไม่ได้เพิ่มรายการใหม่ |
| 🗑 ลบ | ลบผลตรวจรายการนั้นออกจากแฟ้ม (ถามยืนยันก่อน) |
| ลบผู้รับบริการนี้ | ปุ่มมุมซ้ายล่างของหน้าต่าง ลบทั้งแฟ้มพร้อมประวัติทั้งหมด |

* ระหว่างอยู่ในโหมดแก้ไข กล่อง “บันทึกเป็นการตรวจครั้งใหม่” จะถูกซ่อน และมีปุ่ม **ยกเลิกการแก้ไข** ให้กลับสู่โหมดปกติ
* **ผลตรวจรายการสุดท้ายลบไม่ได้** (ปุ่มถูกปิด) เพราะแฟ้มต้องมีค่าสายตาอ้างอิงเสมอ
* ปุ่มแก้/ลบผลตรวจแสดงเฉพาะบทบาทที่มีสิทธิ์ `saveExam` · ปุ่มลบผู้รับบริการตามสิทธิ์ `deleteCustomer`
  และเซิร์ฟเวอร์ตรวจซ้ำทุกครั้ง การซ่อนปุ่มเป็นเพียงเรื่องประสบการณ์ใช้งาน
* หลังลบผลตรวจล่าสุด ระบบจะส่งผลตรวจที่ใหม่ที่สุดที่เหลืออยู่ขึ้นเซิร์ฟเวอร์แทน เพื่อให้ค่าอ้างอิงตรงกัน

Pantoscopic Tilt · Vertex Distance · Face Form Angle · ดัชนีหักเห · โค้ทติ้ง · สี · วิธีเจียร์ขอบ

## 8. ผู้ช่วยแนะนำเลนส์

ชุดกฎทัศนมาตรศาสตร์ที่ประมวลผลในเบราว์เซอร์ทั้งหมด ไม่เรียก API ภายนอก ไม่ส่งข้อมูลลูกค้าออกนอกเครื่อง
และใช้งานได้แม้ไม่มีอินเทอร์เน็ต (ฟังก์ชัน `analyzeConsultation()` ใน `script.js`)

* วินิจฉัยสายตาสั้น/ยาว/เอียง/สายตายาวตามอายุ/ค่าสองข้างต่างกัน (Anisometropia, Antimetropia)
* คำนวณ Spherical Equivalent เพื่อเลือกดัชนีหักเห 1.56 / 1.60 / 1.67 / 1.74 และโครงสร้างเลนส์
* เลือกโค้ทติ้งตามไลฟ์สไตล์ (Blue Control, Photochromic, DriveSafe, Polycarbonate)
* แนะนำทรงกรอบตามรูปหน้า 7 แบบ พร้อมทรงที่ควรเลี่ยงและวัสดุกรอบ
* สร้างบทพูดปิดการขาย และข้อควรระวังในการวัด/ประกอบแว่น
* จับคู่สินค้าในคลังที่ตรงกับดัชนีหักเห/โค้ทติ้งที่แนะนำ

### เหตุผลเชิงวิชาการ (Clinical Reasoning)

ระบบไม่ได้บอกแค่ "แนะนำอะไร" แต่แสดง **ตรวจพบอะไร · ใช้สูตร/เกณฑ์ไหน · ควรทำอะไรต่อ**
ทุกตัวเลขคำนวณจากสูตรที่ตรวจสอบย้อนกลับได้ (ฟังก์ชัน `buildClinicalReasoning()`)

| หัวข้อ | สูตร / เกณฑ์ที่ใช้ |
| --- | --- |
| กำลังเพ่งตามอายุ | **Hofstetter**: ต่ำสุด = 15 − 0.25×อายุ · เฉลี่ย = 18.5 − 0.30×อายุ · สูงสุด = 25 − 0.40×อายุ |
| ความเหมาะสมของ ADD | **หลักสงวนกำลังเพ่งครึ่งหนึ่ง**: ADD = ความต้องการที่ระยะทำงาน − (กำลังเพ่ง ÷ 2) |
| ช่วงระยะที่มองชัดผ่านโซนใกล้ | ขอบไกล = 100 ÷ ADD · ขอบใกล้ = 100 ÷ (ADD + กำลังเพ่งที่ยังใช้ได้) |
| ปริซึมแนวดิ่งขณะอ่าน | **กฎของ Prentice**: Δ = c × F · เกิน 1.00Δ ถือว่ามีนัยสำคัญ |
| ภาพสองข้างต่างขนาด | ~1.5% ต่อความต่าง 1.00 D · เกิน 3% เริ่มมีอาการ · เกิน 5% มักทนไม่ได้ |
| ชดเชยระยะ Vertex | F′ = F / (1 − x·F) · ใช้เมื่อกำลัง ≥ 4.00 D |
| ความคลาดสีตามขวาง | TCA = ปริซึม ณ จุดที่มอง ÷ ค่า Abbe · เกิน 0.10Δ เริ่มสังเกตเห็น |
| ความโค้งหน้าเลนส์ | **สูตรของ Vogel**: กำลังบวก BC = SE + 6.00 · กำลังลบ BC = SE/2 + 6.00 |
| ผลของสายตาเอียงที่ไม่แก้ | ความพร่ามัวคงเหลือ = CYL ÷ 2 (ตำแหน่งวงกลมความสับสนน้อยที่สุด) |

**การจำแนกภาวะสายตา** ใช้ Spherical Equivalent รายข้าง ไม่ใช่ SPH ดิบ เพราะ SE คือตำแหน่ง
circle of least confusion จึงสะท้อนภาวะสายตาโดยรวมได้ตรงกว่าเมื่อมีสายตาเอียงร่วมด้วย
พร้อมจำแนกชนิดสายตาเอียงตามโฟกัสทั้งสองแกน (Simple / Compound myopic · Simple / Compound
hyperopic · Mixed) และทิศทางแกน (WTR / ATR / Oblique)

> **เรื่องเลนส์กรองแสงสีฟ้า:** ระบบระบุตามตรงว่างานทบทวนวรรณกรรมเชิงระบบหลายฉบับสรุปตรงกันว่า
> หลักฐานปัจจุบันยังไม่เพียงพอที่จะบอกว่าเลนส์กรองแสงสีฟ้าช่วยลดอาการล้าตาได้
> สาเหตุที่มีหลักฐานรองรับคืออัตราการกะพริบตาที่ลดลงและภาระการเพ่งค้างนาน
> ระบบจึงแนะนำกฎ 20-20-20 และการตรวจค่าสายตาระยะกลางเป็นหลัก และเสนอเลนส์กรองแสงสีฟ้า
> เป็นทางเลือกเพื่อความสบายตาเท่านั้น **ไม่ใช่ในฐานะการรักษา** — เพื่อไม่ให้พนักงานขายอ้างเกินหลักฐาน

## 10. Backend บน Google Apps Script (`Code.gs`)

> ไฟล์นี้ **ยังไม่ได้เชื่อมกับหน้าเว็บ** — หน้าเว็บปัจจุบันยังอ่าน Google Sheets แบบ read-only ผ่าน gviz
> ต้องแก้ `script.js` ให้เรียก API นี้จึงจะใช้งานร่วมกันได้

### การติดตั้ง

1. **สำรองไฟล์ก่อน** — ไฟล์ › สร้างสำเนา
2. เปิดสเปรดชีต → **ส่วนขยาย › Apps Script** → วางเนื้อหา `Code.gs` ทับไฟล์เดิม → บันทึก
3. รีเฟรชสเปรดชีต จะมีเมนู **OptiCare** ขึ้นมา
4. เมนู **OptiCare › ติดตั้งฐานข้อมูลครั้งแรก** — สร้างชีตที่ยังไม่มี พร้อมหัวตารางและชีต `_Schema`
5. ถ้าขั้นที่ 4 แจ้งว่ามีชีตถูกข้าม → ทำตามหัวข้อ **การย้ายข้อมูลจากโครงสร้างเดิม** ด้านล่าง
6. เมนู **OptiCare › สร้าง API Token** — เก็บ token ที่ได้ไว้ (สร้างใหม่ = token เดิมใช้ไม่ได้ทันที)
7. **Deploy › New deployment › Web app** · Execute as: **Me** · Who has access: **Anyone**

### การย้ายข้อมูลจากโครงสร้างเดิม

ถ้าในชีตมีข้อมูลอยู่ก่อนแล้วด้วยโครงสร้างเก่า (เช่นชีต `Customers` ที่เก็บค่าสายตา
`od_sph`…`pd` ไว้ในแถวเดียวกับข้อมูลลูกค้า) **ห้ามเขียนหัวตารางทับเฉย ๆ** เพราะข้อมูลเดิม
จะยังอยู่ตำแหน่งคอลัมน์เดิมแล้วไปอยู่ใต้หัวตารางผิดคอลัมน์

`ensureAllSheets()` จะตรวจเจอกรณีนี้และ **ข้ามชีตนั้นไปพร้อมแจ้งเหตุผล** แทนที่จะเขียนทับ

| ขั้นตอน | เมนู | ผลลัพธ์ |
| --- | --- | --- |
| 1. ดูก่อนว่าจะย้ายอะไรบ้าง | **ดูผลการย้ายข้อมูลเดิม (ยังไม่แก้ไข)** | รายงานจำนวนที่จะย้าย โดยไม่แตะข้อมูลเลย |
| 2. ย้ายจริง | **ย้ายข้อมูลเดิมมาโครงสร้างใหม่** | เปลี่ยนชื่อชีตเดิมเป็น `<ชื่อ>_backup_<วันเวลา>` แล้วสร้างชีตใหม่ตาม HEADERS พร้อมย้ายข้อมูล |
| 3. ตรวจผล | **ตรวจโครงสร้างตาราง** | ควรขึ้น ✅ ครบทุกชีต |

`migrateLegacySheets()` อ่านข้อมูลเดิม **ด้วยชื่อคอลัมน์ ไม่ใช่ตำแหน่ง** จึงไม่เลื่อนคอลัมน์
และแยกค่าสายตาที่เคยอยู่ในแถวลูกค้าออกมาเป็นผลตรวจในชีต `Exams` ให้อัตโนมัติ
พร้อมคำนวณ SE / Anisometropia / Near SPH ให้ด้วย

**ข้อจำกัดที่ต้องตามแก้เอง**

* โครงสร้างเดิมไม่ได้เก็บวันที่ตรวจ ระบบจึงใส่ `examDate` เป็นวันที่ย้ายข้อมูล — ควรแก้ให้ตรงความจริง
* ใบสั่งเดิมไม่มีสำเนาค่าสายตาและพารามิเตอร์แล็บ คอลัมน์ `rx*` / `lab*` จะเป็นค่าว่าง
* ชีตสำรองยังอยู่ในไฟล์ ตรวจสอบความถูกต้องแล้วค่อยลบทิ้งเอง

### ซ่อมบำรุงฐานข้อมูล (ปุ่มเดียวจบ)

ถ้าไม่อยากไล่เลือกเมนูเอง ใช้ **ปุ่มซ่อมบำรุงฐานข้อมูล** ซึ่งตรวจทุกชีตแล้วเลือกวิธีซ่อมให้เอง

เข้าถึงได้ 3 ทาง

* หน้าเว็บ › ไอคอนเฟืองบนการ์ด **การเชื่อมต่อฐานข้อมูล** › ปุ่ม **ซ่อมบำรุงฐานข้อมูล**
* หน้าเว็บ › หน้าต่างรายงานการเชื่อมต่อ › ปุ่ม **ซ่อมบำรุงฐานข้อมูล** (อยู่ตรงที่เห็นปัญหาพอดี)
* สเปรดชีต › เมนู **OptiCare › 🛠 ซ่อมบำรุงฐานข้อมูล**

ทำงาน 2 จังหวะเสมอ: **ตรวจและแสดงแผนก่อน → ถามยืนยัน → ค่อยลงมือ**
ขั้นตรวจไม่แตะไฟล์เลย จึงกดดูได้ปลอดภัยทุกเมื่อ

| สภาพที่ตรวจเจอ | วิธีซ่อม | ข้อมูลเดิม |
| --- | --- | --- |
| ไม่พบชีต | สร้างใหม่พร้อมหัวตาราง | — |
| หัวตารางว่างทั้งแถว | เขียนหัวตารางตาม HEADERS | ไม่กระทบ |
| คอลัมน์ตรงอยู่แล้ว | ไม่แตะต้อง | ไม่กระทบ |
| `Customers` โครงสร้างเดิม (มี `od_sph`) | `migrateLegacySheets()` แยกค่าสายตาออกเป็นชีต `Exams` | สำรองชีตเดิมเป็น `_backup_` ก่อน |
| ลำดับคอลัมน์ไม่ตรงแบบอื่น | `repairSheetHeaders()` ย้ายข้อมูลตาม **ชื่อคอลัมน์** | คงไว้ทุกคอลัมน์ที่ชื่อตรงกับ HEADERS |
| `Users` ยังเป็นโครงเดิมที่ใช้อีเมล | เพิ่มคอลัมน์ `username`/`passwordHash` แล้ว**ตั้งชื่อผู้ใช้จากอีเมลให้อัตโนมัติ** | ชื่อ บทบาท และอีเมลเดิมอยู่ครบ |

> บัญชีที่ย้ายมาจากโครงสร้างเดิม (เช่น `somchai.p@example.com` → ชื่อผู้ใช้ `somchai.p`)
> **ยังไม่มีรหัสผ่าน** จึงเข้าระบบไม่ได้จนกว่าจะใช้เมนู **ตั้งรหัสผ่านใหม่ให้ผู้ใช้**
> ถ้าชื่อชนกันระบบเติมเลขต่อท้ายให้ (`somchai.p2`) และบัญชีที่ไม่มีอีเมลจะได้ชื่อจากรหัสผู้ใช้แทน

คอลัมน์ที่ไม่มีอยู่ใน HEADERS จะถูกทิ้ง — ระบบจะ**บอกชื่อคอลัมน์เหล่านั้นในขั้นตรวจ**
ก่อนให้ยืนยัน และหลังซ่อมเสร็จจะตรวจซ้ำอีกรอบ ถ้ายังไม่ผ่านจะรายงานว่าชีตไหนเหลืออยู่

สิทธิ์: `repairPreview` เปิดให้ `owner`/`admin` ส่วน `repairDatabase` เฉพาะ `owner`
บทบาทอื่นกดไม่ได้ และถ้ายิง API ตรงข้ามหน้าเว็บ เซิร์ฟเวอร์ก็ปฏิเสธ

### HEADERS — แหล่งอ้างอิงเดียวของโครงสร้าง

ค่าคงที่ `HEADERS` ใน `Code.gs` เป็นตัวกำหนดคอลัมน์ของทุกชีต **ทั้งลำดับและชนิดข้อมูล**
ทุกฟังก์ชันดึงโครงสร้างจากที่นี่ที่เดียว ไม่มีการฮาร์ดโค้ดดัชนีคอลัมน์ที่อื่นเลย

| การทำงาน | ฟังก์ชัน | ใช้ HEADERS อย่างไร |
| --- | --- | --- |
| สร้างชีต | `ensureAllSheets()` | เขียนแถวหัวตาราง ใส่ note ภาษาไทย ตรึงแถวแรก ตั้งรูปแบบคอลัมน์วันที่ |
| อ่าน | `readAll()` / `readOne()` | จับคู่คอลัมน์ตามลำดับ แล้วแปลงชนิดข้อมูลด้วย `coerceFromCell_()` |
| เขียน | `upsertRecord()` / `appendRecord()` | เรียงค่าตามลำดับ HEADERS ด้วย `toRow_()` เติมค่า default และ `updatedAt` ให้ |
| ตรวจสอบ | `validateSchema()` | เทียบหัวตารางจริงกับ HEADERS — รายงานคอลัมน์ขาด เกิน และลำดับที่สลับ |
| ตรวจข้อมูล | `validateRecord()` | ตรวจ required / enum / ชนิดข้อมูล / รูปแบบวันที่ ก่อนเขียนทุกครั้ง |
| ซ่อม | `repairSheetHeaders(sheet)` | เรียงคอลัมน์ใหม่ตาม HEADERS โดยจับคู่จากชื่อเดิม ข้อมูลไม่หาย |
| ย้ายข้อมูลเก่า | `migrateLegacySheets()` | อ่านโครงสร้างเดิมด้วยชื่อคอลัมน์ แล้วเขียนใหม่ตาม HEADERS |
| กันเขียนทับ | `headerConflict_()` | ถ้าชีตมีข้อมูลและลำดับไม่ตรง จะไม่เขียนหัวตารางทับ แต่แจ้งเตือนแทน |

เพิ่มคอลัมน์ใหม่ = เพิ่มบรรทัดใน `HEADERS` → รัน "ติดตั้งฐานข้อมูล" หรือ `repairSheetHeaders()`
ชีต `_Schema` จะอัปเดตคำอธิบายภาษาไทยให้อัตโนมัติ

### API

ทุกคำขอต้องแนบ `token` · action ที่เขียนข้อมูลเรียกได้เฉพาะ **POST**

| action | วิธีเรียก | หน้าที่ |
| --- | --- | --- |
| `ping` / `schema` / `validate` | GET | ตรวจการเชื่อมต่อ · ดูโครงสร้าง · ตรวจความถูกต้องของชีต |
| `dashboard` | GET | KPI ยอดขาย กำไรขั้นต้น งานแล็บค้าง รายชื่อถึงกำหนดตรวจซ้ำ |
| `listCustomers` / `getCustomer` | GET | รายชื่อพร้อมผลตรวจล่าสุด · แฟ้มเดียวพร้อมประวัติทั้งหมด |
| `listProducts` / `listOrders` / `getOrder` / `listExams` / `listStockMoves` | GET | อ่านข้อมูล (กรองด้วย `category`, `status`, `customerId`, `lowStock`) |
| `saveCustomer` / `saveProduct` / `saveExam` | POST | บันทึก (มี `id` = อัปเดต, ไม่มี = สร้างใหม่) |
| `createOrder` | POST | เปิดบิล + ตัดสต็อก + บันทึก StockMoves ภายใต้ `LockService` |
| `updateOrderStatus` | POST | เปลี่ยนสถานะ · ยกเลิกแล้วคืนสต็อกอัตโนมัติ |
| `adjustStock` | POST | รับเข้า/ปรับ/ตัดสต็อกพร้อมบันทึกที่มา |
| `upload` | POST | อัปโหลดไฟล์ base64 เข้าโฟลเดอร์ Drive แล้วผูก URL กลับเข้าข้อมูล |
| `pullAll` | GET | **ดึงทุกตารางในคำขอเดียว** (customers · exams · products · orders) — ใช้แทนการเรียก 4 action |
| `deleteCustomer` | POST | **ลบออกจากชีตจริง** พร้อมผลตรวจทั้งหมดของคนนั้น (ส่ง `purgeOrders: true` เพื่อลบใบสั่งด้วย) |
| `deleteOrder` | POST | **ลบใบสั่งออกจากชีตจริง** และคืนสต็อกให้อัตโนมัติ |
| `deleteProduct` | POST | **ลบออกจากชีตจริง** พร้อมประวัติสต็อก — ถ้ามีใบสั่งอ้างอยู่จะปิดการใช้งานแทนแล้วแจ้งกลับ |
| `deactivateCustomer` / `deactivateProduct` | POST | ซ่อนจากรายการโดยไม่ลบข้อมูล (soft delete) |
| `bootstrap` / `repair` | POST | สร้างชีต · ซ่อมลำดับคอลัมน์ |

**ตัวอย่างเรียกจาก JavaScript**

```javascript
// อ่าน — GET
const res = await fetch(`${WEB_APP_URL}?action=listProducts&token=${TOKEN}`);
const { ok, data } = await res.json();

// เขียน — POST (ต้องใช้ text/plain ไม่งั้นเบราว์เซอร์จะยิง preflight ซึ่ง Apps Script ไม่รองรับ)
await fetch(WEB_APP_URL, {
  method: 'POST',
  headers: { 'Content-Type': 'text/plain;charset=utf-8' },
  body: JSON.stringify({ action: 'saveProduct', token: TOKEN, record: { name: 'กรอบใหม่', category: 'Frame', price: 4500 } })
});
```

หน้าเว็บที่เปิดจากไฟล์ `file://` ใช้ **JSONP** ได้: `?action=ping&token=...&callback=myFn`

### ข้อควรระวังด้านความปลอดภัย

* Web app ที่ตั้ง "Anyone" คือ URL สาธารณะ — **session token คือด่านที่กันคนอื่นเข้าถึงฐานข้อมูล**
  และ token จะออกให้ก็ต่อเมื่อกรอกชื่อผู้ใช้กับรหัสผ่านถูกต้องเท่านั้น ไม่มี token ฝังไว้ในหน้าเว็บ
* ตั้งรหัสผ่านของพนักงานให้ต่างกันทุกคน อย่าใช้บัญชีเดียวร่วมกันทั้งร้าน
  เพราะ `ActivityLog` จะแยกไม่ออกว่าใครเป็นคนแก้ข้อมูล
* ควรเสิร์ฟหน้าเว็บผ่าน **https** เพื่อไม่ให้รหัสผ่านถูกดักระหว่างทาง
  (GitHub Pages เป็น https อยู่แล้ว)
* **การลบเป็นการลบออกจาก Google Sheets จริง กู้คืนไม่ได้** — สำรองไฟล์ (ไฟล์ › สร้างสำเนา) ก่อนลบข้อมูลจำนวนมาก
  สิทธิ์ลบเปิดให้เฉพาะ `owner` และ `admin`

### ความเร็วในการเข้าสู่ระบบและดึงข้อมูล

การเรียก Apps Script Web App แต่ละครั้งมี**ค่าใช้จ่ายคงที่สูง** (เปิดสคริปต์ · ตรวจสิทธิ์ · เปิดสเปรดชีต)
และ Google **จำกัดจำนวนการรันพร้อมกันต่อผู้ใช้หนึ่งคน** การยิงหลายคำขอพร้อมกันจึงมักถูกจับคิวรันทีละอัน
รวมเป็นหลายเท่าของค่าใช้จ่ายคงที่ — ตัวเลขที่ต้องลดจึงคือ **จำนวนรอบ ไม่ใช่ขนาดข้อมูล**

| จังหวะ | เดิม | ตอนนี้ |
| --- | --- | --- |
| กดปุ่มเข้าสู่ระบบ → ข้อมูลขึ้นจอ | 5 คำขอ (`login` + 4 ตาราง) | **1 คำขอ** (`login` แนบข้อมูลมาด้วย) |
| เปิดหน้าเว็บโดยมีเซสชันเดิม | 5 คำขอ (`me` แล้วค่อยดึง 4 ตาราง) | **2 คำขอ ยิงพร้อมกัน** (`me` + `pullAll`) |
| กดปุ่มดึงข้อมูลเอง | 4 คำขอ | **1 คำขอ** (`pullAll`) |

* หน้าเว็บส่ง `withData: true` ไปกับ `login` เซิร์ฟเวอร์จึงแนบข้อมูลทั้งหมดกลับมาในคำตอบเดียวกัน
  (ยกเว้นบัญชีที่ยังต้องตั้งรหัสผ่านใหม่ — จะยังไม่ได้ข้อมูลจนกว่าจะตั้งเสร็จ)
* ถ้าเซิร์ฟเวอร์ยังเป็น `Code.gs` รุ่นเก่าที่ไม่มี `pullAll` หน้าเว็บจะ**ถอยไปเรียกทีละตารางให้อัตโนมัติ**
  ระบบยังใช้งานได้ปกติ เพียงแต่ช้ากว่า — **Deploy `Code.gs` ใหม่เพื่อให้ได้ความเร็วเต็มที่**

### การลบข้อมูล — อะไรหายไปบ้าง

หน้าเว็บจะ **ลบที่เซิร์ฟเวอร์ให้สำเร็จก่อนเสมอ** แล้วจึงลบในเครื่อง
ถ้าเซิร์ฟเวอร์ลบไม่สำเร็จ ระบบจะไม่แตะข้อมูลในเครื่องเลยและแจ้งเตือน — ป้องกันไม่ให้ข้อมูลสองฝั่งไม่ตรงกัน

| ลบอะไร | หายตามไปด้วย | เก็บไว้ | เหตุผล |
| --- | --- | --- | --- |
| ผู้รับบริการ | ผลตรวจทั้งหมดของคนนั้นในชีต `Exams` | ใบสั่งในชีต `Orders` | ใบสั่งเป็นหลักฐานการขาย และเก็บ**สำเนาชื่อลูกค้า**ไว้ในตัวเองแล้ว จึงยังอ่านรู้เรื่อง |
| ใบสั่ง | — | ความเคลื่อนไหวสต็อก | ระบบคืนสต็อกกรอบ/เลนส์ให้อัตโนมัติ พร้อมบันทึกรายการ `RETURN` ไว้เป็นร่องรอย |
| สินค้า | ความเคลื่อนไหวสต็อกของสินค้านั้น | — | ถ้ามีใบสั่งอ้างถึงอยู่ **จะลบไม่ได้** ระบบปิดการใช้งานให้แทนแล้วแจ้งกลับ |

ทุกการลบถูกบันทึกลงชีต `ActivityLog` ด้วย action `DELETE` พร้อมจำนวนรายการที่หายไป

ถ้าต้องการแค่ซ่อนจากรายการโดยเก็บข้อมูลไว้ ให้เรียก `deactivateCustomer` / `deactivateProduct` แทน

> **หมายเหตุสำหรับผู้พัฒนา:** การลบหลายแถวพร้อมกันใช้ `deleteRows_()` ซึ่งลบ**จากแถวล่างขึ้นบน**เสมอ
> เพราะ `deleteRow()` ของ Sheets ทำให้แถวที่อยู่ถัดลงไปเลื่อนเลขขึ้นหนึ่งตำแหน่ง
> ถ้าลบจากบนลงล่างด้วยเลขแถวที่อ่านมาครั้งเดียว จะลบผิดแถวและทำข้อมูลของคนอื่นหายไปด้วย

## 11. หมายเหตุการพัฒนาต่อ

### ข้อควรระวังเรื่อง `.hidden` กับ Tailwind

`styles.css` มีกฎ `.hidden { display: none }` ไว้กัน element กะพริบก่อน Tailwind Play CDN
ฉีดสไตล์เข้ามา **ห้ามใส่ `!important` ในกฎนี้** เพราะจะทับ responsive variant ทุกตัว
(`md:flex`, `sm:block`, `lg:inline`, `xl:inline`) ทำให้ element ที่ตั้งใจให้โผล่เมื่อจอกว้าง
ถูกซ่อนถาวร — เมนูฝั่งเดสก์ท็อป ชื่อผู้ใช้ที่ล็อกอิน และป้ายกำกับปุ่มจะหายไปทั้งหมด

ส่วนกรณี `hidden` อยู่คู่กับ `flex`/`grid` บน element เดียวกัน (modal, toast, ปุ่มที่สลับด้วย JS)
ไม่ต้องบังคับอะไร เพราะ Tailwind เรียง `.hidden` ไว้หลัง `.flex` ในสไตล์ชีตของตัวเองอยู่แล้ว
กฎ `!important` เหลือไว้เฉพาะ `[hidden]` ซึ่งเป็นแอตทริบิวต์ของ HTML และไม่มี variant ใดอ้างถึง

### โครงของหน้าต่าง modal

หน้าต่างฟอร์มยาว (ลูกค้า · ใบสั่ง · สินค้า) ใช้โครง 3 ชั้นที่นิยามไว้ใน `styles.css`

```
.modal-panel   ล็อกความสูงไว้ที่ calc(100dvh - 2rem) และเป็น flex column
  .modal-head  หัวข้อ — อยู่กับที่
  .modal-form  flex column · min-height: 0
    .modal-body  เนื้อหา — เลื่อนได้เฉพาะส่วนนี้
    .modal-foot  ปุ่มบันทึก — อยู่กับที่
```

**อย่าเอา `overflow-y-auto` กลับไปใส่ที่ฉากหลังคู่กับ `items-center`** — เมื่อเนื้อหาสูงกว่าจอ
flexbox จะดันส่วนหัวขึ้นไปเหนือจุดเริ่มต้นของพื้นที่เลื่อน ทำให้เลื่อนกลับไปดูหัวข้อไม่ได้เลย
(อาการคือหน้าต่างโดนตัดทั้งบนและล่าง) โครงปัจจุบันแก้ปัญหานี้และทำให้ปุ่มบันทึกอยู่ในสายตาตลอด

ถ้าเพิ่ม modal ใหม่ที่เนื้อหายาว ให้ใช้โครงเดียวกัน และอย่าลืม `min-height: 0`
บน flex item ที่มีลูกเลื่อนได้ ไม่งั้นเบราว์เซอร์จะไม่ยอมหดให้

### จุดตัดของเมนู

เมนูแนวนอนบนแถบหัวแสดงที่ `lg` (≥1024px) ขึ้นไป ต่ำกว่านั้นใช้แถบเมนูล่างแทน
ถ้าจะเพิ่มเมนูหรือแก้ข้อความบนปุ่ม ให้ตรวจว่าที่ความกว้าง 1024px ปุ่มยังอยู่บรรทัดเดียว
(ปุ่มทุกตัวมี `whitespace-nowrap` ถ้าข้อความยาวเกินจะดันจนล้นกรอบสูง 64px แทนที่จะตัดบรรทัด)
ค่าที่วัดได้ปัจจุบัน: ที่ 1024/1280/1440px ปุ่มสูง 36px อยู่บรรทัดเดียว ไม่มีแถบเลื่อนแนวนอน

### โลโก้ร้าน

`logo.png` สร้างจากไฟล์ต้นฉบับ 1254×1254 โดยครอบเป็นวงกลม (จุดศูนย์กลาง 631,622 รัศมี 600)
แล้วทำพื้นนอกวงให้โปร่งใสพร้อมลบรอยหยักที่ขอบ จึงวางบนพื้นน้ำเงินเข้มของแถบหัวได้โดยไม่เห็นกรอบสี่เหลี่ยม
ถ้าเปลี่ยนโลโก้ ให้คงขนาด 256×256 และความโปร่งใสนอกวงไว้ แล้วทำ `apple-touch-icon.png` 180×180
แบบพื้นทึบคู่กันด้วย

### อื่น ๆ

* Tailwind Play CDN เหมาะกับการสาธิต หากขึ้น production ควรติดตั้ง Tailwind CLI/PostCSS
  แล้ว build ไฟล์ CSS จริง (จะได้ไฟล์เล็กลงมากและไม่มี warning ใน console)
* ตรรกะทั้งหมดอยู่ใน IIFE เดียวและไม่มีตัวแปร global — ถ้าจะขยายเป็นหลายไฟล์
  ให้เปลี่ยนไปใช้ ES Modules (`<script type="module">`) ซึ่งต้องรันผ่านเว็บเซิร์ฟเวอร์
* จุดที่ควรทำต่อเมื่อใช้งานหลายสาขา: ย้ายข้อมูลไปฐานข้อมูลฝั่งเซิร์ฟเวอร์, ระบบสิทธิ์ผู้ใช้,
  พิมพ์ใบสั่งงานแล็บ/ใบเสร็จเป็น PDF, กราฟแนวโน้มค่าสายตารายบุคคล,
  บันทึกผลตรวจเพิ่มเติม (Binocular vision, Tonometry, Keratometry), ระบบนัดหมายและแจ้งเตือนตรวจซ้ำอัตโนมัติ
